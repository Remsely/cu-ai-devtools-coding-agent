# Защита: сценарий от «включил компьютер» до конца демонстрации

Линейная последовательность. Команды — для Git Bash из корня репозитория
(далее `<repo>`). То, что печатается вручную в диалоге агента, помечено `ВВОД>`.

---

## 1. Запуск Ollama

```bash
# сервер уже поднят? (после установки Ollama стартует сама)
curl -s http://localhost:11434/api/tags | head -c 100
```

Не отвечает → запустить (подождать ~10 сек и повторить curl):

```bash
"$LOCALAPPDATA/Programs/Ollama/ollama.exe" serve &    # или ярлык «Ollama» в Пуске
```

Модели на месте? → в списке `qwen3.5:9b` и `qwen3:8b`:

```bash
"$LOCALAPPDATA/Programs/Ollama/ollama.exe" list
```

> Контекст 65536 уже настроен навсегда (`setx OLLAMA_CONTEXT_LENGTH 65536`)
> и подхватывается запущенным сейчас процессом. Трогать не нужно.

## 2. Автотесты runtime (~30 сек)

```bash
python -m pytest tests -q        # ожидание: 47 passed
```

## 3. Smoke живой модели (~15 сек)

```bash
python -m agent run --task "Проверка связи: вызови Bash с командой echo ok \
и заверши работу кратким ответом." --no-input
# ожидание: Думает… → Bash(echo ok) → Ответ: … → ✔ Готово. (exit 0)
```

## 4. Демо 1 — контрольная задача (главное, ~2 мин)

```bash
rm -rf runs && git checkout -- workspace/order.py
python -m agent
```

```
ВВОД> Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй.
```

Смотрим: `Думает… → list_files → read_file ×2 → план`.

```
ВВОД> y          ← утверждение плана (до этого побочных действий не было)
```

Смотрим: чеклист `[~]`/`[x]`, `write_file`, `Bash(python -m unittest -v)`,
`complete_task`, `✓ задача … подтверждена`, `✔ Готово`.

```
ВВОД> tasks      ← чеклист + фактическая команда проверки каждой задачи
ВВОД> diff       ← unified diff order.py + хеши
ВВОД> status     ← бюджет, вызовы с task_id, решения
ВВОД> exit
```

Проверка результата:

```bash
python -m unittest discover -s workspace -v   # OK — фикс реален
git diff --stat workspace/test_order.py      # пусто — тесты не тронуты
```

## 5. Демо 2 — сбой и восстановление (~2 мин)

```bash
rm -rf runs && git checkout -- workspace/order.py
AGENT_FAILPOINT=after_execute python -m agent
```

```
ВВОД> Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй.
```

Процесс падает (exit 70) на первом инструменте — до плана. Чат показывает
карточку неопределённого вызова и спрашивает решение:

```
ВВОД> r          ← retry: новая попытка того же tool_call_id
ВВОД> y          ← утверждение плана (вопрос придёт после восстановления)
```

Смотрим: `retry → … → ✔ Готово`.

```
ВВОД> exit
```

Журнал (WAL) после восстановления:

```bash
RUN=$(ls runs | tail -1)
python -m agent status $RUN    # попытки, решения пользователя, бюджет не обнулился
```

## 6. Демо 3 — откат и конфликт (~1 мин)

Используем запуск из демо 2 (order.py изменён агентом):

```bash
echo "# посторонняя правка" >> workspace/order.py
python -m agent rollback $RUN
# → ✖ конфликт отката: файл правили извне, exit 6, НИЧЕГО не перезаписано

sed -i '/посторонняя правка/d' workspace/order.py
python -m agent rollback $RUN
# → ✓ откат: восстановлено ['order.py']

python -m unittest discover -s workspace   # FAILED = исходная баг-версия возвращена
```

## 7. Демо 4 — бюджеты (~30 сек)

Исчерпание запросов к модели:

```bash
rm -rf runs
python -m agent run --plan --script demo/checkpoint_script.json \
    --no-input --limits '{"model_requests": 2}'
echo $?    # 3 = limit_reached
```

Пачка целиком при нехватке tool_calls:

```bash
rm -rf runs
python -m agent run --plan --script demo/checkpoint_script.json \
    --auto-approve --limits '{"tool_calls": 2}'
# → read_file(order.py)      [отклонено: BUDGET_EXCEEDED]
# → read_file(test_order.py) [отклонено: BUDGET_EXCEEDED]
```

## 8. Завершение

```bash
rm -rf runs && git checkout -- workspace/order.py   # проект в исходном виде
# остановить Ollama (если нужно освободить VRAM):
taskkill /IM "ollama app.exe" /F; taskkill /IM "ollama.exe" /F
```

## Запасной план: нет модели / нет сети

Всё то же самое без Ollama — добавить `--script demo/checkpoint_script.json`
и запускать `python -m agent chat …`. Порядок ввода тот же (`y`, `r`, `y`).

# Приложения (справочно, не для прогона)

## А. Коды завершения

| Код | Значение |
|---|---|
| 0 | завершено / ожидание утверждения плана |
| 3 | limit_reached (бюджет) |
| 4 | aborted (пользователь / отклонён план) |
| 5 | failed (ошибка API, три текст-ответа подряд без инструментов) |
| 6 | конфликт отката (посторонние правки) |
| 70 | управляемый сбой (failpoint) |

## Б. Покрытие требований задания

| Требование | Где показывается |
|---|---|
| Блок 1: agent loop, Bash, инструменты, пачки, ошибки | демо 1 + автотесты |
| Блок 2: WAL, неопределённый вызов, retry/skip/abort, идемпотентность | демо 2 + `test_recovery.py` |
| Блок 3: Plan Mode, ноль побочных эффектов до утверждения | демо 1/2 + `test_plan_mode_blocks_all_side_effects` |
| Уровень 8: 4 лимита, пачка целиком, обрезка, счётчики после resume | демо 4 + `test_budget.py` |
| Уровень 9: задачи, зависимости, подтверждение runtime-ом, чеклист | демо 1 (`tasks`) + `test_tasks.py` |
| Уровень 10: снапшоты, diff, откат, конфликт | демо 3 + `test_changes.py` |
| Тесты контрольного проекта не меняются | `git diff --stat` в демо 1 |

## В. Типовые вопросы → где смотреть в коде

| Вопрос | Ответ | Код |
|---|---|---|
| Почему модель выбрала инструмент? | Модель сама по descriptions/JSON Schema; runtime валидирует имя и аргументы до выполнения | `tools/base.py`, `loop.py: _handle_batch` |
| Что при ошибке инструмента? | Конверт с кодом последнего достигнутого слоя; цикл не падает | `tools/base.py`, `execute()` |
| Что при исчерпании бюджета? | Действие не начинается; пачка целиком; списание до действия, после сбоя не возвращается | `budget.py`, `loop.py` |
| Что при сбое? | `started` без `finished` = неопределённый вызов; молча не повторяется; retry = новая попытка | `events.py`, `recovery.py` |
| Как подтверждается задача? | Только exit code команды проверки, запускаемой runtime; модель может лишь предложить исправленную команду (`verification_command`) | `tasks.py` |
| Как работает откат? | Снапшот до действия, diff после; сверка хешей перед откатом; конфликт = ничего не трогаем | `changes.py` |
| Как Plan Mode запрещает запись? | Инструментов записи нет в списке tools запроса | `tools/__init__.py` |
| Почему write_file можно повторять? | Полная перезапись идемпотентна + already_applied | `tools/fs.py` |
| Где живёт состояние? | `runs/<run_id>/journal.jsonl`, append-only + fsync; состояние = replay | `events.py`, `state.py` |

## Г. Ключевые обоснования

1. **Единицы бюджета**: model_request = обращение к API; tool_call = исполненный
   вызов; side_effect = вызов с `side_effect=True`; output_bytes = байты JSON
   результатов. Служебные проверки задач бюджет не расходуют — механизм
   runtime, а не действие модели.
2. **Усечённый вывод списывает всю аллокацию** — иначе остаток никогда не
   достиг бы нуля; обрезка помечается `"truncated": true`.
3. **Bash не ограничен списком «безопасных» команд** (сопоставление по тексту —
   не граница): детерминированная граница — снапшоты/хеши дерева.
4. **Исключения снапшотов**: `__pycache__/`, `*.pyc` — генерируемые артефакты,
   исходники и тесты не скрывают.
5. **Защита тестов** — пара «правило + наблюдение»: deny в политике write_file
   + сверка содержимого в acceptance-тесте.
6. **Пустые ответы модели — корневая причина**: Ollama по умолчанию режет
   контекст до `num_ctx = 4096` молча (в server.log — `truncated = 1`); на
   8–10 ходу диалог превышал лимит → обрывок посередине → мгновенный EOS.
   Лечение — `OLLAMA_CONTEXT_LENGTH=65536`. Ретрай пустого ответа в runtime —
   страховка. Хорошая история: симптом → гипотезы → лог сервера → root cause.
