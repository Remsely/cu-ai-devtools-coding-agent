# Шпаргалка для защиты

Демонстрация построена вокруг **живой модели** (Ollama + `qwen3.5:9b`) и
**интерактивного диалога** `python -m agent`. scripted-модель — только как
запасной вариант без интернета (последний раздел).

## Подготовка (один раз, до защиты — ~5 минут)

### 0. Окружение проекта

```bash
cd coding-agent
pip install -r requirements-dev.txt   # только pytest; сам агент — чистый stdlib
python -m pytest tests -q             # 47 passed
```

### 1. Ollama: запуск, проверка, остановка

Модели уже скачаны: `qwen3.5:9b` (основная) и `qwen3:8b` (запасная).
Проверка сервера:

```bash
curl -s http://localhost:11434/api/tags | head -c 120
"$LOCALAPPDATA/Programs/Ollama/ollama.exe" list   # обе модели на месте?
```

Не отвечает → запустить: Windows — «Ollama» из меню Пуск (трей), либо в
терминале `ollama serve`. Linux/macOS — `ollama serve`.

**ВАЖНО — контекст:** на сервере должно действовать
`OLLAMA_CONTEXT_LENGTH=65536` (уже настроено через `setx`, применяется к
новым процессам Ollama). Без него сервер **молча** режет контекст до 4096
токенов — на длинных диалогах модель возвращает пустые ответы (подробности:
README, «Ловушка Ollama»). Если Ollama запускалась до настройки — перезапустить.

Перезапуск с явным контекстом / остановка (освободить VRAM):

```bash
taskkill /IM "ollama app.exe" /F; taskkill /IM "ollama.exe" /F      # остановка
OLLAMA_CONTEXT_LENGTH=65536 ollama serve                            # запуск явно
```

## Демо 1. Агент решает контрольную задачу (главное, ~2 мин)

```bash
python -m agent
```

В диалоге ввести задачу (можно своей формулировкой):

```
задача|команда> Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй.
```

Что происходит на экране (комментировать именно это):

1. «думаю (модель: qwen3.5:9b)» → агент сам вызывает `list_files`, `read_file`
   (инструменты выбирает модель, не сценарий);
2. печатаётся **план**: цель, шаги, инструменты, риски, критерий готовности;
3. вопрос **«Утвердить план? [y]es / [n]o»** → ввести `y`.
   До этого момента побочных действий не было вообще: инструменты записи и
   Bash не передаются модели в фазе планирования;
4. исполнение: чеклист задач `[~]`/`[x]`, агент правит `order.py`, запускает
   тесты через Bash, вызывает `complete_task` — и **runtime сам** запускает
   проверку каждой задачи (exit code), а не верит словам модели;
5. финал: «✔ Готово», итог, изменённые файлы, бюджет.

Проверка результата (то, что требует задание):

```bash
python -m unittest discover -s workspace -v    # тесты зелёные — фикс реален
git diff --stat workspace/test_order.py        # пусто — тесты агент не трогал
```

В том же диалоге (run_id последнего запуска запомнен):

```
задача|команда> diff        # изменения запуска: unified diff + хеши
задача|команда> status      # бюджет, вызовы, задачи, решения
задача|команда> tasks       # чеклист + команда проверки каждой задачи
задача|команда> exit
```

## Демо 2. Сбой между выполнением и сохранением + восстановление

В новом процессе с «взведённой» точкой отказа:

```bash
rm -rf runs && git checkout -- workspace/order.py
AGENT_FAILPOINT=after_execute python -m agent
```

(адресно: `AGENT_FAILPOINT=after_execute:c6` — упадёт на записи файла;
без адреса — на первом исполненном инструменте).

Ввести ту же задачу, утвердить план (`y`). Процесс **упадёт с кодом 70**
ровно между выполнением инструмента и сохранением результата.

> Порядок ввода: без адресации failpoint срабатывает на ПЕРВОМ исполненном
> инструменте (до утверждения плана), поэтому сначала будет вопрос `r/s/a`
> (ввести `r`), и только потом — утверждение плана (`y`).

Диалог в чате продолжится сам — покажет карточку:

```
Неопределённый вызов (начат, результат не сохранён):
  инструмент:   write_file
  наблюдение:   дерево отличается от журнала: order.py — ...
  наблюдение:   файл существует и СОВПАДАЕТ с целевым содержимым
Действие: [r]etry / [s]skip / [a]bort:
```

Ввести `r` → retry оформлен как **новая попытка того же tool_call_id**,
write_file увидит `already_applied` (файл повторно не меняется), работа
доедет до «✔ Готово».

Показать журнал (сердце блокa 2):

```bash
RUN=$(ls runs | tail -1)
grep -c '"event": "tool_call_started"'  runs/$RUN/journal.jsonl
grep -c '"event": "tool_call_finished"' runs/$RUN/journal.jsonl
python -m agent status $RUN    # попытки, решения пользователя, бюджет уцелел
```

Варианты решения (по желанию, на свежих крашах): `s` — шаг неуспешен,
цикл продолжается; `a` — запуск завершается с ошибкой.

Отдельным процессом (как в README): `python -m agent resume <run_id>` —
тот же вопрос `r/s/a`, состояние восстановлено replay-ем журнала.

## Демо 3. Откат изменений и конфликт (уровень 10)

После успешного запуска из демо 1 (или нового):

```bash
python -m agent diff $(ls runs | tail -1)        # что менял этот запуск
echo "# посторонняя правка" >> workspace/order.py
python -m agent rollback $(ls runs | tail -1)    # конфликт, exit 6
head -2 workspace/order.py                       # правка на месте — ничего не перезаписано
sed -i '/посторонняя правка/d' workspace/order.py
python -m agent rollback $(ls runs | tail -1)    # исходный order.py восстановлен
python -m unittest discover -s workspace         # тесты падают = вернули баг-версию
```

Смысл: откат трогает только файлы этого запуска; перед откатом хеши сверяются
с журналом; при посторонней правке не перезаписывается ни один файл.
Откат недоступен, пока не разрешены неопределённые вызовы (потребует сначала
`resume`).

## Демо 4. Бюджеты (уровень 8)

```bash
rm -rf runs
python -m agent run --plan --no-input --limits '{"model_requests": 2}'
echo $?    # 3 = limit_reached
python -m agent status $(ls runs | tail -1)   # счётчики 2/2
```

Пачка целиком при нехватке лимита (c2+c3 не влезают после c1):

```bash
rm -rf runs
python -m agent run --plan --script demo/checkpoint_script.json \
    --auto-approve --limits '{"tool_calls": 2}'
# → read_file(order.py)      [отклонено: BUDGET_EXCEEDED]
# → read_file(test_order.py) [отклонено: BUDGET_EXCEEDED]
# ни один вызов пачки не исполнялся и не списывался; scripted-сценарий
# после этого продолжает запрашивать инструменты — они также отклоняются
# по лимиту (живая модель в такой ситуации меняет стратегию)
```

Счётчики не обнуляются после resume — видно в демо 2 (`status` показывает
запросы, потраченные до сбоя + после).

## Демо 5. Коды завершения

| Код | Значение |
|---|---|
| 0 | завершено / ожидание утверждения плана |
| 3 | limit_reached (бюджет) |
| 4 | aborted (пользователь / отклонён план) |
| 5 | failed (ошибка API, «модель трижды ответила текстом») |
| 6 | конфликт отката (посторонние правки) |
| 70 | управляемый сбой (failpoint) |

## Типовые вопросы → где смотреть в коде

| Вопрос | Ответ | Код |
|---|---|---|
| Почему модель выбрала инструмент? | Модель сама по descriptions/JSON Schema; runtime только валидирует имя и аргументы до выполнения | `tools/base.py`, `loop.py: _handle_batch` |
| Что при ошибке инструмента? | Конверт с кодом последнего достигнутого слоя; цикл не падает | `tools/base.py` (коды), `execute()` |
| Что при исчерпании бюджета? | Действие не начинается; пачка целиком; списание до действия, после сбоя не возвращается | `budget.py`, `loop.py` |
| Что при сбое? | `started` без `finished` = неопределённый вызов; молча не повторяется; retry = новая попытка | `events.py`, `recovery.py` |
| Как подтверждается задача? | Только exit code команды проверки, которую запускает runtime; модель может лишь предложить исправленную команду (`verification_command`) — исполняет всё равно runtime | `tasks.py` |
| Как работает откат? | Снапшот до действия, diff после; сверка хешей перед откатом; конфликт = ничего не трогаем | `changes.py` |
| Как Plan Mode запрещает запись? | Инструментов записи нет в списке tools запроса | `tools/__init__.py` |
| Почему write_file можно повторять? | Полная перезапись идемпотентна + already_applied | `tools/fs.py` |
| Где живёт состояние? | `runs/<run_id>/journal.jsonl`, append-only + fsync; состояние = replay | `events.py`, `state.py` |

## Ключевые обоснования

1. **Единицы бюджета**: model_request = обращение к API; tool_call = исполненный
   вызов; side_effect = вызов с `side_effect=True`; output_bytes = байты JSON
   результатов. Служебные проверки задач бюджет не расходуют — это механизм
   runtime, а не действие модели.
2. **Усечённый вывод списывает всю аллокацию** — иначе остаток никогда не
   достиг бы нуля; обрезка помечается `"truncated": true`.
3. **Bash не ограничен списком «безопасных» команд** (сопоставление по тексту —
   не граница): детерминированная граница — снапшоты/хеши дерева.
4. **Исключения снапшотов**: `__pycache__/`, `*.pyc` — генерируемые артефакты,
   исходники и тесты не скрывают.
5. **Защита тестов контрольного проекта** — пара «правило + наблюдение»:
   deny в политике write_file + сверка содержимого в acceptance-тесте.
6. **Пустые ответы модели — корневая причина найдена**: Ollama по умолчанию
   режет контекст до `num_ctx = 4096` токенов молча (в server.log —
   `truncated = 1`); на 8–10 ходу диалог агента превышал лимит, модель
   получала обрывок посередине и сразу выдавала EOS. Лечение —
   `OLLAMA_CONTEXT_LENGTH=65536` для сервера (в OpenAI API параметра num_ctx
   нет). Ретрай пустого ответа в runtime — страховка, а не основное решение.
   Хорошая история для защиты: симптом → гипотезы (think:false? формат
   сообщений?) → лог сервера → root cause.
