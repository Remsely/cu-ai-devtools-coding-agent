# Coding agent с tool calling

Учебный консольный агент по ДЗ №1: получает задачу на изменение небольшого
проекта, сам выбирает инструменты, читает и меняет файлы, запускает тесты
и решает, когда закончить.

Реализованы все уровни задания:

| Уровень | Что реализовано |
|---|---|
| 7 (база) | Agent loop с tool calling, инструмент `Bash`, восстановление после сбоя, Plan Mode |
| 8 | Единый бюджет запуска, устойчивый к сбоям |
| 9 | План, разбитый на задачи с зависимостями и подтверждением результата |
| 10 | Журнал изменений (снапшоты, diff, хеши) и откат по `run_id` |

Агент написан на Python **только на стандартной библиотеке** (зависимостей
нет), без агентских фреймворков: agent loop, восстановление, бюджеты и
планирование реализованы самостоятельно. `pytest` нужен только для тестов.

## Установка

Требуется Python 3.10+ и `bash` в `PATH` (на Windows — Git Bash или WSL).

```bash
pip install -r requirements-dev.txt   # только pytest
python -m pytest tests -q             # проверка, что всё работает
```

## Модель

Агент работает с любым OpenAI-compatible Chat Completions API. Настройка —
переменными окружения (см. `.env.example`):

```bash
export OPENAI_BASE_URL=https://api.example.com/v1
export OPENAI_API_KEY=sk-...
export OPENAI_MODEL=gpt-4o-mini
```

Локальная Ollama как запасной вариант (ключ — любая непустая строка).
Контрольная задача проверена на `qwen3.5:9b` (лучшие метрики tool calling
в 8–9B классе на конец 2026; ~6 ГБ в 4-bit, помещается в 12 ГБ VRAM):

```bash
ollama pull qwen3.5:9b   # запасной вариант из задания: ollama pull qwen3:4b
ollama serve
# .env: OPENAI_BASE_URL=http://localhost:11434/v1/, OPENAI_API_KEY=ollama,
#       OPENAI_MODEL=qwen3.5:9b
```

Доп. параметры API (JSON) — через `AGENT_LLM_EXTRA`, например
`AGENT_LLM_EXTRA={"think": false}` отключает рассуждения qwen3.x на стороне
Ollama (системный промпт агента уже содержит `/no_think`).

Для демо и тестов без сети используется детерминированная
scripted-модель: `--script demo/checkpoint_script.json` — список реплик
модели (вызовы инструментов или текст), которые она выдаёт по одной.

## Набор инструментов

| Инструмент | Аргументы | Побочный эффект | Безопасно повторять |
|---|---|---|---|
| `list_files` | `path?` | нет | да |
| `read_file` | `path` | нет | да |
| `write_file` | `path`, `content` | да | да (см. ниже) |
| `Bash` | `command`, `cwd?` | да | **нет** |
| `submit_plan` | `plan` | нет (только Plan Mode) | да |
| `complete_task` | `task_id` | нет (только исполнение) | да (завершённая не перепроверяется) |

Каждый инструмент передаётся модели с именем, описанием и JSON Schema
аргументов; runtime проверяет имя и аргументы **до** выполнения. Результат
возвращается сообщением `role: tool` с исходным `tool_call_id`. Один ответ
модели может содержать несколько tool calls (пачка).

Границы `Bash`: лимит времени (`AGENT_BASH_TIMEOUT`, по умолчанию 60 с; при
таймауте завершается вся группа процессов), лимит размера вывода (лишнее
обрезается с пометкой `truncated`), чистое окружение — дочернему процессу
передаётся только allowlist переменных (`PATH`, `HOME`, `LANG`, системные
переменные Windows); секреты, включая `OPENAI_API_KEY`, не наследуются.

**Повторяемость инструментов** (обоснование для блока 2):
- `list_files`, `read_file`, `submit_plan` — не имеют эффектов, повтор безопасен;
- `write_file` — полная перезапись: те же аргументы дают то же состояние;
  повторная запись того же содержимого не меняет файл (`already_applied: true`);
- `Bash` — команда могла изменить файлы или внешнее состояние, безопасного
  повтора нет: повтор только по явному решению пользователя;
- `complete_task` — повтор для уже завершённой задачи возвращает сохранённый
  результат проверки без повторного запуска.

## Запуск агента

Контрольная задача (демо на scripted-модели, без сети):

```bash
python -m agent run --plan --script demo/checkpoint_script.json --auto-approve
```

С реальной моделью:

```bash
python -m agent run --plan --task "Исправь расчёт итоговой стоимости заказа..."
```

Полный список команд:

```
python -m agent run     --task TASK [--plan] [--auto-approve] [--limits JSON]
                        [--failpoint after_start|after_execute] [--script FILE]
python -m agent approve RUN_ID      # утвердить план и начать исполнение
python -m agent reject  RUN_ID      # отклонить план
python -m agent resume  RUN_ID [--decision retry|skip|abort] [--script-skip N]
python -m agent status  RUN_ID      # состояние, бюджет, задачи, изменения
python -m agent tasks   RUN_ID      # чеклист задач (уровень 9)
python -m agent diff    RUN_ID      # изменения запуска (уровень 10)
python -m agent rollback RUN_ID     # откат изменений запуска (уровень 10)
```

## Plan Mode и утверждение плана

`run --plan` запускает режим планирования: модели доступны **только**
инструменты чтения (`list_files`, `read_file`) и `submit_plan`. Инструменты
записи и `Bash` в фазе планирования не передаются модели вообще, поэтому
побочный эффект до утверждения невозможен по конструкции (это проверяется
тестом `test_plan_mode_blocks_all_side_effects`).

План — структурированные данные, сохраняются событием `plan_saved` вместе
с `run_id`: цель, шаги (описание, зависимости, инструменты, команда
проверки), риски, допущения, критерий готовности. После сохранения запуск
переходит в состояние `awaiting_approval` и ждёт явного решения:
интерактивный вопрос, `--auto-approve` или команда `approve`/`reject`.
Исполнение начинается только после утверждения.

## Восстановление по run_id (блок 2)

Всё состояние запуска — append-only журнал `runs/<run_id>/journal.jsonl`
(одно событие — строка JSON, запись с fsync). Текущее состояние — детерминированный
replay журнала, поэтому `resume` восстанавливает историю сообщений, tool
calls, результаты, решения пользователя, бюджет, задачи и журнал изменений.

Ключевой паттерн — write-ahead: перед действием с побочным эффектом пишется
`tool_call_started`, после — `tool_call_finished`. Падение между ними даёт
«неопределённый» вызов: он **не** повторяется молча. `resume` показывает
карточку вызова (аргументы, а для `write_file` — совпадает ли уже файл с
целевым содержимым) и предлагает решение:

1. `retry` — явный повтор: **новая попытка** того же `tool_call_id`
   (для `write_file` повтор не меняет файл повторно — идемпотентность);
2. `skip` — шаг считается неуспешным, работа продолжается;
3. `abort` — запуск завершается с ошибкой.

Не начатые до сбоя вызовы той же пачки помечаются `NOT_EXECUTED_AFTER_CRASH`
(без этого история осталась бы без role=tool ответов). Повтор моделью
`tool_call_id` с теми же аргументами возвращает сохранённый результат без
исполнения; с другими аргументами — ошибка протокола `PROTOCOL_ERROR`.

Управляемые точки отказа для демонстрации (работают и в тестах):

```bash
AGENT_FAILPOINT=after_execute python -m agent run ...   # сбой между выполнением и сохранением
python -m agent run --failpoint after_start ...         # сбой после записи started, до исполнения
# адресно: AGENT_FAILPOINT=after_execute:c6
```

## Бюджеты (уровень 8)

Единый бюджет на все фазы одного `run_id` (планирование, исполнение,
восстановление); `resume` счётчики не обнуляет. Единицы счёта:

- `model_requests` — обращения к Chat Completions;
- `tool_calls` — исполненные вызовы инструментов (после валидации);
- `side_effects` — вызовы инструментов с побочным эффектом (`write_file`, `Bash`);
- `output_bytes` — суммарный размер результатов инструментов.

Настройка: `--limits '{"tool_calls": 5}'` (значения сохраняются в журнале
и восстанавливаются при `resume`). Списание — ДО действия и атомарно вместе
с его состоянием: после сбоя бюджет не возвращается; исчерпанный лимит не
пускает действие. Пограничные случаи:

- не хватает остатка на **всю пачку** tool calls — не выполняется ни один
  вызов (`BUDGET_EXCEEDED`);
- размер результата заранее неизвестен — инструмент получает доступный
  остаток, вывод обрезается и помечается `truncated: true`; усечённый
  результат списывает весь выделенный остаток, поэтому следующий вызов при
  нулевом остатке не стартует.

Служебные проверки задач (уровень 9) запускаются runtime-ом и бюджетом
агента не считаются: это механизм подтверждения, а не действие модели.

## Задачи с зависимостями (уровень 9)

После утверждения плана шаги становятся задачами runtime: id, описание,
зависимости, состояние (`pending → in_progress → completed`), проверяемый
результат. Задача стартует только после завершения зависимостей
(последовательного исполнения достаточно). Каждый tool call фазы исполнения
связан с текущей задачей (`task_id` в событии `tool_call_started`); вызовы
фазы планирования хранятся без `task_id`.

Задачу закрывает **только runtime**: модель вызывает `complete_task(task_id)`,
runtime сам запускает команду проверки из плана и при совпадении кода
завершения пишет `task_completed` с фактическим результатом. Заявление
модели «готово» ничего не закрывает; финальный текст при открытых задачах
возвращается модели с замечанием. Чеклист задач печатается в stdout:

```
[чеклист]
  [x] t1 Изучить workspace: order.py и test_order.py
  [~] t2 Исправить calculate_total: процентная скидка и валидация 0..100
  [ ] t3 Запустить тесты и убедиться, что они зелёные
```

Просмотр состояния: `python -m agent tasks RUN_ID`. После `resume`
завершённые задачи не запускаются заново и не перепроверяются
(`test_completed_tasks_not_restarted_after_resume`).

## Журнал изменений и откат (уровень 10)

В начале фазы исполнения runtime сохраняет исходный снимок дерева
(`runs/<run_id>/snapshots/`: содержимое файлов + список путей + sha256).
Перед **каждым** побочным действием (`write_file`, `Bash`) текущее дерево
сверяется с последним сохранённым состоянием и сохраняется снимок ДО
действия; после — фиксируются фактический diff и хеши (`change_recorded`).
Расхождение = посторонняя правка: действие останавливается с
`TREE_MODIFIED_EXTERNALLY`, агент получает наблюдение и решает, что делать.

Просмотр изменений: `python -m agent diff RUN_ID` — по каждому файлу
исходное состояние до первого изменения, итоговое после последнего, хеши
и unified diff.

Откат: `python -m agent rollback RUN_ID` — восстанавливает **только** файлы,
изменённые этим запуском. Перед откатом текущие хеши сверяются с журналом:
если хотя бы один файл правили извне после последнего действия агента —
конфликт, не перезаписывается ничего. Откат недоступен, пока не разрешены
неопределённые после сбоя вызовы; эффект неопределённого вызова относится
к запуску решением пользователя (`retry`/`skip`) и фиксируется в журнале
изменений с `attribution: undefined_call`.

Исключения для генерируемых файлов (явные, не скрывают исходники и тесты):
`__pycache__/`, `*.pyc/.pyo`, `.git/`, `.pytest_cache/`, `runs/`.

## Запуск тестов

```bash
python -m pytest tests -q
```

Тесты полностью офлайн (scripted-модель) и покрывают: контрольную задачу
end-to-end (`test_checkpoint.py`), инструменты и границы `Bash`
(`test_tools.py`), журнал и replay (`test_state.py`), бюджеты и оба
пограничных случая (`test_budget.py`), сбои и решения пользователя
(`test_recovery.py`), задачи и верификацию (`test_tasks.py`), снапшоты,
diff, откат и конфликты (`test_changes.py`).

## Формат состояния

```
runs/<run_id>/
  journal.jsonl          # append-only журнал событий (источник истины)
  snapshots/snap<N>.json # снимки дерева: {path: {hash, content}}
```

События журнала: `run_started`, `budget_debited`, `model_response`,
`tool_call_started/finished/refused/replayed`, `plan_saved/approved/rejected`,
`decision_recorded`, `user_note`, `run_finished`, `tasks_created`,
`task_started/completed`, `snapshot_saved`, `change_recorded`,
`rollback_performed`. Ошибка инструмента несёт код последнего достигнутого
слоя: `PARSE_ERROR` → `INVALID_ARGUMENTS` → `UNKNOWN_TOOL` →
`DENIED_BY_POLICY`/`BUDGET_EXCEEDED`/`TREE_MODIFIED_EXTERNALLY` →
`HANDLER_ERROR` (`FILE_NOT_FOUND`, `TIMEOUT`, …).

## Архитектура

```
cli.py          подкоманды run/resume/approve/reject/status/tasks/diff/rollback
loop.py         agent loop: модель → валидация → бюджет → WAL → исполнение
state.py        состояние = fold событий журнала (event sourcing)
events.py       append-only WAL-журнал с fsync
budget.py       счётчики и проверки единого бюджета
planning.py     схема плана и валидация
tasks.py        задачи, зависимости, верификация runtime-ом, чеклист
changes.py      снапшоты дерева, diff, откат, конфликты
recovery.py     неопределённые вызовы, решения пользователя
llm.py          ScriptedModel и OpenAI-compatible клиент (stdlib)
tools/          реестр, JSON Schema, fs, Bash, submit_plan, complete_task
workspace/      контрольный проект (order.py, test_order.py)
```

Ключевые решения: одно хранилище-журнал на все уровни (WAL блока 2 даёт
атомарность бюджета уровня 8, события задач уровня 9 и снапшоты уровня 10);
политика фаз — инструменты записи не передаются модели в планировании;
защита `test_order.py` — правило + наблюдение (deny в политике и сверка
содержимого в acceptance-тесте); пути проверяются после `resolve()` через
`is_relative_to`, а не строковым префиксом.
