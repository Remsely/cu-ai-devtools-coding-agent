# AgentLens: инструмент для разбора своего агента

**Хочу выяснять, какие неуспешные команды агент повторяет и что делает между
попытками, чтобы выбирать изменения инструкций о проверках и проверять их пользу.**

Поддерживаемый harness — собственный `agent/` из ДЗ №1, формат
`runs/<run_id>/journal.jsonl`. Анализатор — отдельная программа `agentlens/`.
Итог: [инженерный разбор и решение по гипотезе](REPORT.md).
Для демонстрации: [сценарий защиты с командами и пояснениями](../DEFENSE2.md).
Воспроизводимые материалы сдачи: [исходный разбор](reports/discovery/report.md),
[ручная сверка](MANUAL_CHECK.md), [протокол A/B](PROTOCOL.md),
[результаты сравнения](reports/comparison/report.md).

## Быстрый старт: без модели и ключа

Запускайте из корня репозитория на Python 3.10+. У анализатора только стандартная
библиотека; установка пакетов, Bash, Docker и сеть для `analyze` не нужны.

```bash
# Набор из трёх реальных сессий
python -m agentlens analyze --input evals/sessions/discovery/

# Одна реальная сессия с повторяющимися ошибками
python -m agentlens analyze --input evals/sessions/discovery/d02/trace/r20261121-164856-5846/journal.jsonl

# Машиночитаемый результат
python -m agentlens analyze --input evals/sessions/discovery/ --json
python -m agentlens analyze --help

# Для автоматических тестов нужен pytest
python -m pip install -r requirements-dev.txt
python -m pytest tests -q
```

Реальные примеры: [одна сессия — текст](reports/examples/session.txt),
[JSON](reports/examples/session.json), [каталог — текст](reports/examples/directory.txt),
[JSON](reports/examples/directory.json). Повторный анализ можно делать сколько
угодно раз: утилита только читает журналы и не исполняет записанные команды.

## Формат входа и ошибки

Один файл — одна сессия, UTF-8 JSONL (BOM допустим): JSON-объект в каждой
непустой строке. Обязательны строковый `event` и положительный возрастающий
целый `seq`. Первая запись — `run_started` с непустым `run_id`.
Начала инструментов содержат `id`, `name`, `attempt` и строку `args_json` с
JSON-объектом аргументов; результаты — тот же ID/attempt и объект `result`.
Источник формата — `agent/events.py`, `agent/loop.py`, `agent/tasks.py`.

Каталог обходится рекурсивно по `*.jsonl`, без перехода по символьным ссылкам
на каталоги. Снапшоты `*.json` не разбираются. Подготовка/переписывание журналов
не требуется: можно передать непосредственно `runs/` своего агента.

Неизвестные типы событий не исполняются. Пропуски `seq`, незавершённая сессия,
отсутствующий результат или усечённый вывод явно отражаются предупреждениями.
Пропуски, несопоставленные результаты и неоднозначные события разрывают цепочки
повторов. Неизвестный исход не становится
успехом, ошибкой или нулевым измерением.

Коды выхода:

- `0` — анализ завершён; отсутствие находок также корректный результат.
  Оборванная, но синтаксически корректная сессия может иметь предупреждения.
- `2` — неверный/нечитаемый вход. При ошибке одного файла остальные результаты
  сохраняются, сводка помечается неполной, проблемный файл перечисляется.
- `130` — пользователь прервал анализ.

С `--json` stdout содержит один JSON-объект; технические ошибки идут в stderr.
При повреждённой строке анализируется только корректный префикс, с ошибкой
входа и ненулевым кодом. Дубли с одинаковым run_id не удваивают выборку.

## Собственный метод

1. Сопоставляем `tool_call_started/finished` по `(id, attempt)`. Возврат
   сохранённого результата (`tool_call_replayed`, `already_completed`) не считаем
   новым исполнением. Отказ до выполнения также не является исполненной командой.
2. Извлекаем команды Bash и реальные проверки `complete_task`, включая ошибки
   из `result.error.data.verification`. Для Bash неуспех — ненулевой код либо
   таймаут; `result.ok=true` не гарантирует успешность команды. Для проверки
   сравниваем код с `expect_exit_code`: ожидаемый ненулевой код может быть успехом.
3. Собираем цепочки: точный текст команды, записанный каталог, ожидаемый и
   фактический код, таймаут и точная сохранённая диагностика без внешних пробелов.
   Успех, неизвестный исход или другая диагностика той же команды разрывают цепочку.
4. Для цепочек минимум из двух исполнений показываем все адреса событий,
   инструменты и зарегистрированные изменения между ними. `repeat_count = n - 1`;
   суммарный показатель — `summary.repeated_failures`.

Это собственная логика сопоставления и выделения эпизодов, а не пересылка JSON
в LLM. Причину и полезность повторов метод не устанавливает. Произвольная
Bash-команда не объявляется тестом только по своему имени.

## Схема JSON v1

Полный реальный ответ приложен выше; основные поля:

| Поле | Значение |
|---|---|
| `schema_version`, `question`, `method` | Версия, исследуемый вопрос, правило и ограничения |
| `complete` | Нет ошибок входа и предупреждений о полноте сведений |
| `summary` | Размер выборки, исполнения, неуспехи, неизвестные исходы, эпизоды и повторы |
| `sessions[]` | `session_id`, исходный файл, задача, статус, предупреждения, исполнения и находки |
| `executions[]` | Команда, cwd, инструмент, ID/attempt, состояние, фактический/ожидаемый код, вывод |
| `findings[]` | Команда и сигнатура, `occurrences`, `repeat_count`, интервалы `between` |
| `start`, `result` | Устойчивые адреса `{seq, line}`; отсутствующий результат — `null` |
| `between[].actions/changes` | Действия и пути/хеши изменений с адресами событий |
| `errors[]` | Исходный файл, сообщение, номер строки при наличии |

Текстовый вывод содержит те же находки, счётчики и предупреждения; длинные
цепочки сокращены до первых двух и последнего исполнения. Все события доступны
в JSON и исходном файле. `unknown_executions` и `uncomparable_failures` показывают,
когда отсутствие находок не означает отсутствие возможных повторов.

## Ограничения и проверка метода

Разные shell-записи одной команды, алиасы путей и динамический текст ошибок
не объединяются. Это может пропустить похожие ошибки. Совпавший сохранённый
хвост вывода не доказывает общую первопричину. Помеченную усечённую диагностику
не сопоставляем; для runtime-проверок хвост от 800 символов считаем потенциально
усечённым. Чтение/изменение файла между повторами показывается как контекст,
но не превращает повтор автоматически в лишний или оправданный.

Синтетические журналы явно помечены в `tests/test_agentlens.py`: положительный
случай с основаниями, разные cwd, разные ожидаемые коды, успешный запуск между
ошибками, отсутствие результата, replay/retry, таймауты, усечение, повреждённые
события и CLI. `tests/test_evals.py` проверяет независимые graders на исходном,
исправленном и заведомо неполном решении, матрицу и границы Docker.
Ручная сверка реального эпизода находится в [MANUAL_CHECK.md](MANUAL_CHECK.md).

## Воспроизведение реальных запусков

Для новых запусков нужны Docker с Linux-контейнерами, локальный/доступный
OpenAI-compatible сервер модели и параметры из `.env.example`. В сохранённом
опыте использованы Ollama `qwen3.5:9b`, temperature 0.2, think false,
context 65536; digest — [model.json](model.json). Не публикуйте `.env` и ключи.
Фактический контекст работающей модели сохранён в [runtime-model.json](runtime-model.json);
максимальный контекст модели из model.json и настройка сервера — разные величины.

```bash
docker pull python:3.12-slim

# Три исходные сессии (новый каталог)
python -m evals.batch discovery --output evals/sessions/my-discovery

# 12 новых попыток по зафиксированному протоколу; каталог не перезаписывается
python -m evals.batch compare --output evals/sessions/my-comparison --instruction-file evals/variants/changed.txt

# Повторный разбор сохранённого сравнения без модели/Docker
python -m evals.report --input evals/sessions/comparison --output evals/reports/comparison --comparison
```

Точный digest использованного образа сохранён в [image-digests.json](image-digests.json).
Для повтора на закреплённом образе передайте его значение через `--image`;
обычный тег `python:3.12-slim` со временем может измениться.

У `evals.report` код `0` означает отчёт без замечаний о данных/условиях,
`1` — отчёт создан, но есть перечисленные замечания, `2` — ошибка построения.
Код `0` у batch означает завершённую запись партии, а не успех всех задач;
смотрите результаты каждой попытки и итоговый разбор.

Runner сохраняет журналы в `trace/`, чтобы они не попадали под игнорирование
`runs/`. В каждой попытке есть manifest, архив агента, agent.log, итоговые файлы,
вывод независимого grader и result.json. Сравнение проверяет одинаковость модели,
настроек, исходных файлов, кода, grader, образа и единственность изменения
системной инструкции. Полное время, количество вызовов и неизвестные токены
сохраняются по каждому запуску.

Изолированы оба пути исполнения команд: инструмент Bash и runtime-проверка.
Контейнер не получает сеть, секреты, домашний каталог или Docker socket.
Тесты доступны только для чтения; отдельный grader проверяет больше граничных
случаев и запускается с workspace только для чтения. Обычный `python -m agent`
сохраняет прежний способ исполнения: эта изоляция включена в экспериментальном runner.
